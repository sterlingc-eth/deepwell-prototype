## 1. Known bug — fixed: pricing CTA loses `?plan=` before Clerk loads

**Root cause**: `useDeepLink`'s effect fires on mount, before Clerk resolves,
applies the plan to the (in-memory) zustand store, and scrubs the address
bar back to a bare `/app/`. That's fine as long as nothing reloads the page —
but a brand-new user's flow *does* reload it: Clerk's OAuth sign-in and
`CreateOrganization`/`OrganizationList` both do a real top-level navigation
away and back, landing on whatever `signUpFallbackRedirectUrl`/
`afterCreateOrganizationUrl`/`afterSelectOrganizationUrl` named — always the
static string `"/app/"`. That reload throws away the in-memory store (fresh
JS heap) *and* lands on a URL with no `?plan=` to re-parse, so the chosen
plan never reaches Billing.

**Fix**:
- `src/hooks/useDeepLink.ts` — persists the raw query string to
  `sessionStorage` (key `deepwell.pendingDeepLink`) the moment the module
  loads (before React/Clerk run), wrapped in try/catch. `useDeepLink` now
  takes a `ready` boolean (`isSignedIn && !!orgId`); it still applies
  plan/screen/entity/doc/work immediately as before (harmless — nothing
  renders until `ready` anyway), but only *clears* the persisted copy once
  `ready` is true, so it survives however many sign-in/org-creation redirects
  happen first. New exports: `resolveDeepLinkRedirectPath` (pure — live
  search wins, falls back to the persisted copy) and `deepLinkRedirectTarget`
  (impure wrapper).
- `src/App.tsx` — `useDeepLink(!!isSignedIn && !!orgId)`.
- `src/screens/LoginScreen.tsx` — `fallbackRedirectUrl`/
  `signUpFallbackRedirectUrl` now `deepLinkRedirectTarget()` instead of the
  static `"/app/"`.
- `src/screens/OnboardingScreen.tsx` — same for `CreateOrganization`'s
  `afterCreateOrganizationUrl` and `OrganizationList`'s
  `afterSelectOrganizationUrl`/`afterCreateOrganizationUrl`.
- `scripts/verify-ui.ts` — 6 new cases for `resolveDeepLinkRedirectPath`.

### 1a. Reviewer NO-GO — fixed: stale persisted plan could resurrect

**Finding**: the persisted copy above had no expiry and was only ever
cleared once `ready` (signed in with an org). Someone who abandons signup
after clicking a pricing CTA, then later opens `/app/` from a bookmark **in
the same tab/session**, would get that stale `?plan=` silently re-applied to
Billing — completely unrelated to what they're doing now.

**Fix** (`src/hooks/useDeepLink.ts`):
- The persisted entry is now `{ search, ts }` (JSON), not a bare string.
  `DEEP_LINK_TTL_MS` = 15 minutes. `freshPersistedDeepLinkSearch(raw, now)`
  (new pure export) returns the search string only when `now - ts` is within
  the TTL — otherwise `''`, exactly as if nothing were persisted.
- `readAndPruneStalePersistedSearch()` (impure) uses that, and additionally
  **deletes** a stale/corrupt entry the moment a bare load finds nothing
  fresh to use — a bare `/app/` visit with no redirect in flight never
  leaves a leftover entry for a later visit to trip over.
- Every real sighting of the link live (module load, or a redirect landing
  back on the same `?plan=...` URL) re-persists with a fresh `ts`, so the
  clock resets on legitimate progress through a slow multi-step signup
  rather than counting down from the very first click.
- Consumption still clears the entry outright (not just lets it expire): the
  existing `ready`-gated effect in `useDeepLink`, **plus** a new effect in
  `src/App.tsx` that calls the newly-exported `clearPersistedDeepLinkSearch()`
  as soon as `billingStatus.status` is `'active'` or `'trialing'` — so it
  can't outlive its own purpose even inside the 15-minute window.
- `scripts/verify-ui.ts` — 10 new cases for `freshPersistedDeepLinkSearch`:
  within-TTL bare load → applied; past-TTL → ignored; exact boundary
  (inclusive) and one ms past it; nothing persisted; corrupt JSON; future
  timestamp (clock skew) treated as stale; the old pre-TTL plain-string
  format dropped rather than honored forever; and the "consumed once → a
  second read after clearing gets nothing" sequence.

## 4. Noted, not fixed (product decisions / low-priority)

- `api/_lib/routes/keys.js`, `merge-tenant.js`, `tenant-export.js`,
  `tenant-delete.js` have no rate limit. All four are admin-gated (or
  solo-tenant-is-its-own-admin), low-frequency, deliberate actions — lower
  risk than `notifications.js` (member-reachable, auto-polled), which is why
  only that one got a contained fix. Worth a rate limit pass if the owner
  wants defense-in-depth here too, but each is its own judgment call on
  bucket/limits — flagging rather than guessing.
- `NotificationsPanel`'s `markNotificationsRead`/`markAllNotificationsRead`
  calls end in `.catch(() => {})` after an optimistic local update — a
  failed write is silently corrected on the next 5-minute poll (the item
  reverts to unread) rather than surfacing a toast. Self-healing and very
  low stakes; flagging per the audit brief's "swallows errors silently"
  criterion rather than adding a toast for a bell-icon mark-read.
- `IntegrityPanel`'s new "Retire shop-address records" button intentionally
  never joins `ALL_INTEGRITY_FIXES`/cron's auto-apply list — same
  reasoning as `relinkMismatchedNames` (unlinking documents from a customer
  isn't something to eyeball-undo), so it stays a manual, explicit action.
